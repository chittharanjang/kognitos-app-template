# 1. Yes/No Questions (Single DB) — FIDO, Profile Status
# Concise Yes/No answer in email body. No file attachment.
#
# As of v1.19, yes/no portal-access questions are PHRASING-AGNOSTIC.
# All of these route through the same strict-match composer and report
# the actual `online_portal_access` value:
#
#   Canonical:        "Does Liam Johnson have portal access?"
#   Possessive:       "Liam's portal access?", "rahul's portal-access?"
#   No leading verb:  "rahul portal access?", "john smith portal access?"
#   Case-insensitive: "rahul mehta portal access?", "f1010 portal access?"
#   Hyphenated:       "Rahul's portal-access?"
#   Synonym:          "is rahul registered?", "rahul registered?"
#
# Behavior:
#   - 0 matches → NDF: "No — <Name> was not found in the system."
#   - 1 match  → "Yes/No — <Full Name> [does not] have portal access."
#   - 2+ matches → "Multiple clients match '<token>': <names>. Please
#                  specify a full name or a fiduciary ID."
#
# Examples on the seed dataset:
#   - "Does John Smith have portal access?"   → NDF (no John Smith in DB)
#   - "Does John Doe have portal access?"     → No  (opa=False, F1031)
#   - "Does Liam Johnson have portal access?" → Yes (opa=True,  F1010)
#   - "Does F1010 have portal access?"        → Yes (Liam Johnson)
#   - "rahul's portal access?"                → Yes (Rahul Mehta, F1028)
#   - "Is John registered?"                   → No  (John Doe, opa=False, F1031)
#   - "is priya nair registered?"             → No  (Priya Nair, opa=False)
#
# v1.20: per-sub-question pre-intercept + expanded stopwords prevent
# words like `id`, `email`, `give`, `his`, `phone` from leaking into
# name claims. Multi-question queries like
# "Is John registered? Also give me his email ID." now split correctly
# (sub-Q1 = portal yes/no for John Doe; sub-Q2 = his email via pronoun
# resolution). Same release: v1.17 IRA subtype-refinement now also
# applies to the data-retrieval path, so
# "Give me clients with Inherited Roth IRA accounts." returns 4 (the
# 4 Inherited Roth IRA clients only — not 11 = Roth+Inherited Roth).
#
# v1.21: the "registered" verb path now resolves the name BEFORE
# checking opa (was filtering opa=True first, dropping unregistered
# clients before the name lookup). "Is X registered?" works for both
# opa=True and opa=False targets.
#
# v1.22 (2026-05-01): comprehensive name-extractor stopword expansion
# + multi-question planner-state isolation. The portal/registered
# yes/no name extractor previously leaked status/object/greeting
# tokens (`open`, `closed`, `active`, `inactive`, `system`,
# `database`, `hi`, `thanks`, `named`, `you`, `we`, `profile`,
# `allowed`, `granted`, `roth`, `ira`, ...) into name claims,
# producing NDFs like "John Open not found", "Database not found",
# "Hi Thanks not found", "We Smith not found", "Named Smith not
# found", "John Allowed not found", "Priya Granted not found".
# v1.22 added ~110 tokens to both `yn_pre_sw` and
# `yn_claim_stopwords` (covering verbs, status words, account-type
# words, greetings/sign-offs, request verbs, pronouns), restored a

# empty-claims-fall-through edit (this had broken every "Is X
